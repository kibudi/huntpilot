The problem

Job hunting is a pipeline, and everyone tracks it in a spreadsheet they stop updating after two weeks.

  • Where did I apply, and when?
  • Which ones have gone quiet and need a follow-up?
  • What's actually worth applying to today?

Solving it for myself. If it's genuinely useful, I'll actually keep using it — which is the only way the project survives past week one.

What it is

One backend, two ways in.

  • Web dashboard — the full picture. Table of every application, status, notes, outcomes.
  • Discord bot — the daily driver. /jobs new to see fresh matches, /apply to log one, and it DMs me when something's gone quiet.
  • Background worker — polls job boards on a schedule, queues new matches, fires the follow-up reminders.

The bot is what makes it stick. Opening a dashboard is a chore; replying to a DM isn't.

Why this project

  • Real reason to run more than one service — so containers and orchestration aren't decoration.
  • Real reason to have a queue and a scheduler — polling job boards is genuinely async work.
  • Frontend, backend, database, infra — the whole stack, end to end.
  • It's a portfolio piece about job hunting, built while job hunting.

The DevOps half

The actual point of the project.

  • Containers — each service in its own image, Compose to wire them locally.
  • Orchestration — real Kubernetes on kind: Deployments, Services, ConfigMaps, Secrets, and an HPA scaling the worker on queue depth.
  • CI/CD — GitHub Actions: lint and test on PR, build and push images on merge.
  • IaC — Terraform: modules, state, providers. Applied against LocalStack.

The part that isn't a tracker

Job boards tell you what is open today. Nobody records what changed.

  • The role I applied to has disappeared — it is filled. Stop waiting on it.
  • Applied 30 days ago and the posting is still live — silence is not rejection.
  • Same job reposted every six weeks — churn, or a spec nobody can meet.

None of these are answerable from a single snapshot. They need board state stored over time and joined against the application log — which this project already has. That join is the differentiator.

The sweep

Three systems publish a company's open roles as JSON — no key, no scraping: Greenhouse, Lever, Ashby.

gatewhat it dropscost
0–1  fetch + normalisethree payload shapes into onefree
2  reconcilenothing — this gate is the productfree
3  location279 → 78free
5  title (whitelist of five role families)290 → 30free
5b  stack + years (reads the description)30 → 7free
4  dedupe · 6  judgedesigned, not built—

Counts from one real sweep of 28 boards: 1,026 postings in, 7 out. The free gates already get to a shortlist, which is why the paid one has not been needed yet.

Closure is inferred, never reported

A board never announces that a role was filled. The entry simply stops coming back.

  • One document per posting for its whole life — a sweep bumps last_seen_at, it does not append. The collection grows with the market, not with time.
  • Boards intermittently omit live entries, so two consecutive misses are required before anything is called closed. Crying wolf here would be worse than saying nothing.
  • A company name is resolved to a board token by guessing — 29 of 69 names answered. vast turned out to be a rocket company in California, not the Israeli storage one, so a human confirms before a board joins the watchlist.
